# Emitted-asm census -- rusty_json_turbo (lib `serde_json`)

This census PRICES BRICKS BEFORE THEY ARE BUILT. It reads the assembly rustc
actually emitted for the library and counts what is there, so that a brick is
opened or closed on evidence instead of on the expectation that a lever exists.
It answers the three questions the mission plan asks of the `.s`:

- **(a) Is there a bounds-check tax worth removing?** The house expectation,
  from h264, rav1e and dds, is that it is about zero. A near-zero result is a
  real finding that CLOSES a brick, not a failed measurement.
- **(b) Are there runtime-length `memcpy` calls on the hot parse/serialize
  paths that a brick could remove?** A source grep finds only the copies
  someone wrote; the `.s` finds the ones the optimiser introduced and the ones
  it failed to fold.
- **(c) Has the compiler already auto-vectorised anything?** If it has, a
  hand-written SIMD twin is competing with the compiler and its claim shrinks
  accordingly; if it has not, the twin is competing with scalar code.

Generated by `tools/asm-census.ps1`. It counts instructions; it never measures
time. See the method line at the end.

## What this census closes and what it opens

Sections 0 to 5 and the method line below are generated verbatim by
`tools/asm-census.ps1`. THIS section is written by hand from those numbers and
is the only part a re-run does not regenerate: re-run the tool with `-Out` to a
scratch path and splice its body back in under this heading.

### (a) Bounds-check tax: not zero, but small, and mostly cold

**63 panic call sites in the whole emitted crate.** Owned by the three files of
interest: `read.rs` 23, `ser.rs` 2, `de.rs` **0**. The remaining 38 belong to
`value/index.rs` (3, the documented panics of the `Index` API), `itoa` (5, its
own internal digit-buffer indexing at `itoa-1.0.18/src/lib.rs:176`, inlined
into `Number: Display` and four `MapKeySerializer::serialize_i*` methods), and
std's `BTreeMap` node code, `str::replace`, `Option::unwrap` and `str` slicing
inside `error::make_error` (30). The 2 sites charged to `ser.rs` are itoa's
too, reached through the `Value: Serialize` chain rather than directly.

`read.rs`'s 23 split into two shapes:

- **6 `panic_bounds_check`, and they are one repeated defect.** All six come
  from three source sites, each with the identical shape "compare the cursor to
  the length with `==`, then index":

  | site | function | copies emitted |
  | --- | --- | ---: |
  | `read.rs:492` | `SliceRead::skip_to_escape_impl` (`self.index == self.slice.len() \|\| is_escape(self.slice[self.index], ..)`) | 2 |
  | `read.rs:569` | `SliceRead::parse_str_bytes` (`if self.index == self.slice.len() { .. } match self.slice[self.index]`) | 3 |
  | `read.rs:945` | `SliceRead::ignore_str` (same shape) | 1 |

  An `==` comparison against `len()` does not hand LLVM the fact `index < len`,
  so the following index re-checks. These six sit inside the hot string
  scanner.
- **17 `slice_index_fail`** from range slicing (`&self.slice[a..b]`). 3 are on
  the cold error/position path (`read::error`, `Deserializer::error`,
  `SliceRead::position`); 14 are in `parse_str` (6), `parse_str_raw` (1),
  `decode_hex_escape` (2), `parse_escape` (2) and `parse_unicode_escape` (3),
  so they are reached only when a string actually contains an escape.

**CLOSED.** `get_unchecked` in `de.rs`. `de.rs` owns zero panic sites in this
instantiation set, so the number and token parser has nothing to unguard, and
the "any `get_unchecked` before the M1 bounds-check census says there is a real
one" line in the mission plan stays closed for that file.

**OPENED.** The six `read.rs` `panic_bounds_check` sites are a named brick, and
a SAFE one: turning the `== len()` guard into a `<`-form comparison (or a
`get()`) lets LLVM fold the branch with no `unsafe` at all. That is
`codec-eliminate-redundancy` work (carry the producer's fact), not
`rusty-unsafe-optimizations` work.

**NOT SAID.** How much time any of this costs. This is a static site count; a
guard in a cold block costs zero. 63 sites is consistent with the house
expectation of a ~0 tax, and the bounds-check-ceiling probe still has to price
it before a single line changes.

### (b) `memcpy`: 46 calls, every one a runtime length, none owned by `ser.rs`

36 `memcpy`, 10 `memmove`, **0 `memset`**. Every one of the 46 has a runtime
length; `const` reads 0 across the table. Three were checked by hand in the
`.s` (`mov r8, rdi`, `mov r8, rsi`, `mov r8, r15` immediately before the call),
so this is a real result and not the classifier failing to see an immediate --
though `const` remains a lower bound by construction, as section 3 states.

Owners: `read.rs` 6, `de.rs` 3, `ser.rs` **0**, other crate files 0, external
37.

- `read.rs`'s 6 are all `core::ptr::copy_nonoverlapping` (`ptr/mod.rs:549`)
  reached through `Vec::extend_from_slice` inside `parse_str` and
  `parse_str_raw` -- the SCRATCH-BUFFER path, taken only for a string that
  contains an escape. The borrowed no-escape fast path emits no copy call at
  all, which is exactly what it should do, and that is the finding.
- `de.rs`'s 3 are all error-path moves of the `Error` value
  (`Option::map` at `core/src/option.rs:1231`, `copy_nonoverlapping` at
  `intrinsics/mod.rs:459`, and the `Err(self.fix_position(err))` return at
  `de.rs:1517`). No payload copy.

**CLOSED / repriced.** `ser.rs` owns **zero** `mem*` calls. Bricks B5 (`to_vec`
sink specialisation) and B15 (fold `,` and `:` into the adjacent write) cannot
be justified as "remove a copy": there is no copy CALL on the serialize path
for them to remove -- the copying there is either an inlined `movups` pair or a
`write_all` loop. This agrees with B5's own M1-A repricing, which already said
it must win on `write_all` COUNT alone. The census now says the same thing from
the other side. `memset` 0 also closes any "we are zeroing buffers we should
not be" hypothesis.

**OPENED.** Nothing new. The 6 `read.rs` copies are the escape path, which B2
already covers, and their length is genuinely dynamic (the run length between
escapes), so no length-folding brick applies.

### (c) Auto-vectorisation: none. The compiler vectorised nothing.

**7 packed instructions in the entire crate**, and neither kind is vector work:

- 5 `punpckldq`, every one loading the same rodata constant
  `__xmm@00000000000000004530000043300000`, which is LLVM's u64-to-f64
  conversion idiom, inside `de.rs` number parsing. Scalar float conversion
  scaffolding.
- 2 `movdqa xmm0, xmm1`, register-to-register moves.
- `pcmpeq*` 0, `pmovmsk*` 0, `pshuf*` 0, `por` 0, `pand`/`pandn` 0, `vp*` 0,
  `vmov*` 0.

A further 267 xmm instructions are separated out on purpose: 207
`movups`/`movaps` 16-byte block moves (inlined struct and buffer copies), 12
register-zeroing ops, 21 `movd`/`movq` transfers and 22 scalar `movss`/`movsd`.
Counting those as SIMD is how a report comes to claim vectorisation that is not
there.

Two things this does NOT prove. The baseline ISA is plain `x86-64` (SSE2):
there is no `.cargo/config.toml`, no `RUSTFLAGS` and no `-C target-cpu` in the
build, so `vp*` = 0 is *expected* and says nothing about what an AVX2 build
would auto-vectorise. And the landed B1s whitespace scan is 8-byte SWAR on
`u64`, not SIMD, so its absence from the packed table is correct -- it is also
a useful control: the census sees exactly what it should and no more.

**OPENED.** Every hand-written SIMD twin on the backlog (B1v, B2, B3, B12) is
competing with SCALAR code, not with the compiler's vectoriser, so none of
their claims is pre-empted. **CLOSED.** "The compiler already did it" is not an
argument against any of them on this build.

### What did not work, stated plainly

1. **No per-file attribution without `-C debuginfo=1`.** The first build, on
   the invocation in the mission plan, emitted a 834,498-byte `.s` with **zero**
   `.loc` and zero `.cv_loc` directives, because the release profile carries no
   debug info. Every count would have been whole-crate. Adding
   `-C debuginfo=1` produced a 2,861,341-byte `.s` with full line tables, and
   that flag is now part of the documented invocation.
2. **DWARF `.loc` never appears on this host.** `x86_64-pc-windows-msvc` emits
   CodeView (`.cv_file` / `.cv_func_id` / `.cv_inline_site_id` / `.cv_loc`).
   The tool reads both forms and the method line records which it found; a
   Linux run of the same tool will report DWARF and, because DWARF `.loc` here
   carries no inline-frame chain, only the `own` column, not `owner`.
3. **Three of the eight symbols the mission plan named do not exist in rustc
   1.98.** `slice_index_len_fail`, `slice_start_index_len_fail` and
   `slice_end_index_len_fail` have been replaced by a single
   `core::slice::index::slice_index_fail`, and `core::str::slice_error_fail`
   handles the `str` case. `panic_misaligned_pointer_dereference`,
   `expect_failed` and `panic_cannot_unwind` are genuinely absent (0), not
   mismatched. All eight rows are kept in section 2 so the difference is
   visible rather than silently folded away.
4. **The struct-parse path is not in this census at all.** `--emit asm` on the
   `--lib` target emits only the instantiations this crate makes of its own
   generics. Every `#[derive(Deserialize)]` monomorphisation lives in the
   consumer crate. What is priced here is the `Value` DOM parse, `Map::from_str`,
   the `Display`/`to_string` serialize paths, `SliceRead`/`StrRead`, and
   everything non-generic. Bricks B6, B6h and B14, which live on the struct
   path, are NOT priced by this run; doing that needs the same tool pointed at
   an `--emit asm` build of the bench binary, and that is not done here.
5. **Counts are pre-LTO.** The profile sets `lto = "thin"` with
   `codegen-units = 1`; asm is emitted per codegen unit before link-time
   optimisation, so the finally linked object can differ.
6. **`ser.rs` owns 3,661 instructions but only 301 are its own lines.** The
   serializer is almost entirely inlined `Vec`/`String` code from `alloc`. That
   is not a defect in the instrument, but it does mean "look at `ser.rs`" in
   the `.s` means "look at what `alloc` does on `ser.rs`'s behalf", and any
   brick there is really a brick about the sink.

### One number to carry forward

`de.rs` + `ser.rs` + `read.rs` own 9,136 of 18,246 emitted instructions
(50.1%), and the 25 largest functions are 66% of the crate. The three largest
are `Value: Serialize::serialize` (twice, once per formatter) and
`Deserializer<StrRead>::deserialize_any` -- the DOM paths, not the scanners.
Code size is not run time, and this line is not a ranking of where time goes;
it is a note that the DOM paths dominate the emitted crate, which is consistent
with the allocation census's verdict at M1-A that DOM parse is
allocation-dominated.

## 3. memcpy / memmove / memset calls

A `call memcpy` that survives optimisation is a copy whose length the optimiser
could not fold away. The length column is read off the length ARGUMENT REGISTER
(r8, the 3rd integer argument on x86_64-pc-windows-msvc) by walking back up to 16
instructions for the last write to it: an immediate operand is `const`, any
other operand is `runtime`, and `unknown` means no write to that register was
found inside the window. So `const` is a LOWER bound and `runtime` an UPPER
bound -- `mov r8, rax` is reported runtime even when `rax` happens to hold a
constant established further back. Copies the optimiser inlined into `movups`
pairs are not calls and are not in this table; see section 4.
