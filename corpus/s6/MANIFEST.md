# S6 -- the pathological corpus

JSONCORP's sixth scenario. `docs/plans/fast_mission.md` 7.2 lists it as
"100-deep nesting, 1 MB single string with escapes every 7 bytes, 1 MB of
`\uXXXX`, 20-digit integers, 400-digit floats", and its gate is not speed:
**"cold paths stay correct and do not regress; error line/col identity"**.

Nineteen files, one hazard per file, so a failure names itself. Eleven are
expected to PARSE and eight are expected to FAIL, and the two groups are kept
apart in three independent places: the `s6-fail-` filename prefix, the table
below, and the `group` column of `SPECS` in `tools/gen-s5-s6.py` (which the
generator enforces).

Everything here is generated by `tools/gen-s5-s6.py` from one fixed seed
(`0x53365F504154484F`). Regenerating is byte-identical; `python
tools/gen-s5-s6.py --check` regenerates in memory and fails if any byte on
disk differs.

---

## READ THIS FIRST: eight of these files must FAIL to parse

`crates/rusty_json_turbo-bench/tests/oracle.rs` compares this crate against
upstream serde_json byte for byte on every corpus document, **including
failures** -- it compares the error's message text, its line, its column and
its `Category`. So a must-fail file is a first-class corpus member and the
strongest test of error identity there is. The same is already true of
`corpus/jsonchecker/fail*.json`; S6 differs only in that its failures are
*semantic* (recursion limit, surrogate pairing, number range) rather than
lexical, and they are planted deep in the file so the LINE and COLUMN are
non-trivial.

None of these eight is a bug. Each one is labelled below with the exact error
upstream produces.

| # | file | bytes | expected `from_slice::<Value>` outcome (MEASURED) |
|---|---|---:|---|
| 12 | `s6-fail-deep-array-128.json` | 257 | `Err(recursion limit exceeded at line 1 column 128)` |
| 13 | `s6-fail-deep-object-128.json` | 33,921 | `Err(recursion limit exceeded at line 128 column 260)` |
| 14 | `s6-fail-lone-trailing-surrogate.json` | 7,328 | `Err(lone leading surrogate in hex escape at line 152 column 23)` |
| 15 | `s6-fail-lone-leading-surrogate.json` | 7,327 | `Err(unexpected end of hex escape at line 152 column 23)` |
| 16 | `s6-fail-unpaired-hex-pair.json` | 7,332 | `Err(lone leading surrogate in hex escape at line 152 column 27)` |
| 17 | `s6-fail-float-overflow.json` | 2,603 | `Err(number out of range at line 152 column 7)` |
| 18 | `s6-fail-int-400-digit.json` | 4,282 | `Err(number out of range at line 152 column 402)` |
| 19 | `s6-fail-exponent-overflow.json` | 2,610 | `Err(number out of range at line 152 column 14)` |

Every column above is the `from_slice` one, and every error is
`Category::Syntax`. Each is reported identically by `from_slice`,
`from_str` and `from_reader` **except two** -- see
`The SliceRead / IoRead column disagreement` below, which is a finding in
its own right.

**One hazard per file, and that is not fussiness.** A parser stops at its
first error, so a file with two hazards only ever tests the first. Eight
mechanisms therefore need eight files.

## The must-PARSE files

### 1. `s6-deep-array-100.json` -- 201 B, depth 100

`[`x100 + `1` + `]`x100. The plan's "100-deep nesting", in its purest form:
99.50% structural bytes, one number token, no strings and no keys at all, so
nothing but `check_recursion!` and the array open/close path is being
measured.

**Must parse.** serde_json's default recursion limit is 128, and 100 is under
it. The exact boundary is file 3.

### 2. `s6-deep-object-100.json` -- 901 B, depth 100

`{"k000":{"k001": ... {"k099":1} ... }}`. Depth 100 with a **distinct key per
level**: 100 keys, 100 distinct strings, key reuse **1.0**. The cold arm of
key dispatch at depth, and the counterpart to file 10, which has the same
depth with reuse 100.

**Must parse.**

### 3. `s6-deep-mixed-127.json` -- 507 B, depth 127

`[{"a":[{"a": ... ]`, alternating array and object to exactly 127 containers:
**the deepest document that parses.** 64 arrays, 63 objects.

**Must parse, and it is the boundary from the passing side.** `remaining_depth`
starts at 128 and `check_recursion!` errors when it reaches 0, so depth 127 is
the last that succeeds and 128 is the first that fails. That is not read off
the source: `tests/test.rs::test_stack_overflow` asserts 127 nested arrays
parse and that `"["x129` reports `recursion limit exceeded at line 1 column
128`, and the outcomes table below confirms both ends on these files.

### 4. `s6-string-escape-7.json` -- 1,048,581 B, one string

A **bare top-level JSON string** -- valid JSON per RFC 8259 -- of 1,048,579
content bytes in which an escape sequence begins **every 7 bytes**: five
literal ASCII bytes, then one two-byte escape, 149,797 times.

Bare, not wrapped in an object, because then nothing else in the file can
absorb the measurement: 100.00% of the bytes are string content, 0 keys, 0
numbers, 0 whitespace, 0 structural bytes beyond the two quotes.

| Escape | Count |
|---|---:|
| `\"` / `\\` / `\/` / `\b` / `\f` | 18,725 each |
| `\n` / `\r` / `\t` | 18,724 each |
| total escape sequences | **149,797** |
| escape bytes as a share of string bytes | **28.57%** (2 of every 7) |
| decoded length | 898,782 characters |

**Prices B2's dirtiest arm.** A wide string scan stops every five bytes;
`s4-ocr-i18n.json` is the realistic case at 17.65% escape bytes and this is
the ceiling at 28.57%. Together with `s4-vault-shard.json`'s clean 87 KB runs
it brackets B2's whole range.

**Prices B3 with an exactly predictable answer.** `\/` is in the cycle on
purpose: it decodes to `/` and is *not* re-escaped on output, so it is the one
escape whose input and output widths differ. The round trip must therefore be
**exactly 18,725 bytes shorter** -- one per `\/`. Measured: upstream's
`to_string` of the parsed value is 1,029,856 bytes against the file's
1,048,581, a delta of 18,725. Python's `json.dumps` agrees to the byte. A B3
that is off by one anywhere shows up as a wrong total here, not as a wrong
character somewhere in a megabyte.

**Must parse.**

### 5. `s6-unicode-escapes.json` -- 1,048,580 B, one string

A bare top-level string that is **nothing but `\uXXXX`**: escape bytes are
100.00% of string bytes. This is the hex decoder's ceiling, where
`s4-ocr-i18n.json` (5,671 escapes, 17.65%) is its realistic case.

| Inventory | Count |
|---|---:|
| `\uXXXX` escapes | **174,763** |
| of those, correctly-paired surrogates (as pairs) | **17,433** |
| single BMP escapes | 139,897 |
| escapes containing an uppercase hex digit | 29,923 |
| `"` (decodes to `"`, must be re-escaped out) | 3,703 |
| `\` (decodes to `\`, must be re-escaped out) | 3,745 |
| control-character escapes below 0x20 | 22,078 |
| decoded code points | 157,330 |
| decoded UTF-8 bytes | 367,581 |

Mixed-case hex is deliberate: the decoder must accept `\uD83D` and `\ud83d`
alike, and a case-folding bug would otherwise never appear on this corpus.
Both `U+10000` (the first astral code point) and `U+10FFFF` (the last code
point that exists) are present and confirmed in the decoded string.

**Prices scratch-buffer growth inside a single string.** 157,330 code points
decoded into one scratch buffer that reaches ~360 KB. Every other escape file
in the corpus decodes into short strings.

**Prices B3's other extreme.** The round trip is **607,167 bytes shorter**
than the input (1,048,580 in, 441,413 out, measured on both upstream and
Python), because `\u65e5` becomes three raw UTF-8 bytes -- but the 3,703
`"`, 3,745 `\` and 22,078 control escapes must come back *out* as
escapes, in serde_json's exact spelling and lowercase hex.

**Must parse.** The generator refuses to emit an unpaired surrogate here:
every pair is written as one atomic chunk and the file is re-checked with a
lone-surrogate regex, because `json.loads` accepts a lone surrogate and
serde_json does not. Lone surrogates live in files 14-16, on purpose.

### 6. `s6-int-20-digit.json` -- 52,610 B

20-digit integers on both sides of the u64 and i64 boundaries, with
self-describing keys so a typed fixture can assert per field, plus 2,000 bulk
tokens (1,000 just inside u64, 1,000 above it) for volume. 76.52% number
bytes, 2,011 tokens, zero floats *in the text*.

**Every token PARSES as a `Value`, and that is the point of the file.** serde_json
falls back to f64 when an integer does not fit u64 or i64, so "outside the
range" is a TYPED outcome, not a parse failure. Measured, per key:

| key | token | `Value` number type |
|---|---|---|
| `i64_max` | 9223372036854775807 | u64 |
| `i64_max_plus_1` | 9223372036854775808 | **u64** (fits u64, not i64) |
| `i64_min` | -9223372036854775808 | i64 |
| `i64_min_minus_1` | -9223372036854775809 | **f64** -9.223372036854776e18 |
| `twenty_digits_smallest` | 10000000000000000000 | u64 |
| `u64_max` | 18446744073709551615 | u64 |
| `u64_max_plus_1` | 18446744073709551616 | **f64** 1.8446744073709552e19 |
| `twenty_nines` | 99999999999999999999 | **f64** 1e20 |
| `twenty_nines_negative` | -99999999999999999999 | **f64** -1e20 |
| `u128_max` | 340282366920938463463374607431768211455 | **f64** 3.402823669209385e38 |
| `u128_max_plus_1` | 340282366920938463463374607431768211456 | **f64**, the same f64 |

The last row is the useful one: two different 39-digit tokens land on the
identical f64, so `Value` cannot distinguish them and only
`oracle::check_number`'s u128/i128 arms can. Both are in the file.

**Prices the overflow-to-f64 fallback** 1,000 times in the bulk array (the
other 1,000 sit just inside u64 and take `parse_integer`'s
`checked_mul(10)` boundary instead). **B4's control:** every token is 20
digits or more, so the 8-digit step's `d8_hits` must be 0 while `d8_calls` is
large.

**Must parse.**

### 7. `s6-float-400-digit.json` -- 83,515 B

400-digit floats and the exponent extremes that stay FINITE: a 400-digit
fraction, 200 integer digits plus 200 fraction digits, a 400-digit significand
with `e-400`, `f64::MAX`, `1e308`, the smallest normal and subnormal, and four
tokens that underflow to zero. 98.05% number bytes, 211 float tokens, plus 200
bulk 400-digit tokens.

**Nothing here is expected to be an infinity, and THAT is the finding.**
serde_json never produces one: `f64_from_parts` and `parse_long_integer` both
check `is_infinite()` and return `NumberOutOfRange` instead. So every
would-be infinity is a must-FAIL document and lives in file 17. Underflow is
different -- it is not an error -- so the zeros are here:

| key | expected |
|---|---|
| `zero_by_underflow_e_minus_400` (`1e-400`) | **0.0** |
| `negative_zero_by_underflow` (`-1e-400`) | **-0.0** |
| `zero_by_underflow_400_zeros` (`0.` + 400 zeros + `1`) | **0.0** |
| `smallest_subnormal` (`4.9e-324`) | 5e-324 (the smallest subnormal, printed short) |
| `f64_max`, `e308`, `e308_neg` | finite, exact |
| `frac_400`, `int_200_frac_200`, `sig_400_small_exp` | finite; 400 digits round to a normal double |

**Prices `parse_long_integer`'s scratch path** at 400 digits, 211 times over,
which is 50x the digit width canada's floats reach.

**Must parse.**

### 8. `s6-exponent-zeros.json` -- 85,222 B

Very long numbers whose exponent is almost all zeros, and `-0`. The exponent
accumulator is `exp = exp * 10 + digit` behind an i32 overflow guard, so a
leading zero never advances it: `1e` followed by 400 zeros is a 403-byte token
whose value is exactly `1.0`.

| key | token | measured value |
|---|---|---|
| `one_e_400_zeros` | `1e` + 400 zeros | 1.0 |
| `one_e_plus_400_zeros_then_5` | `1e+` + 400 zeros + `5` | 100000.0 |
| `one_e_minus_400_zeros_then_5` | `1e-` + 400 zeros + `5` | 0.00001 |
| `float_e_400_zeros_then_5` | `1.5e` + 400 zeros + `5` | 150000.0 |
| `zero_e_400_zeros` | `0e` + 400 zeros | 0.0 |
| `zero_e_overflowing_exponent` | `0e99999999999999999999` | **0.0** -- a zero significand survives an exponent that overflows i32 |
| `one_e_minus_overflowing_exponent` | `1e-99999999999999999999` | **0.0** -- a negative exponent survives it too |
| `negative_zero_int` | `-0` | **f64 -0.0** -- see below |
| `negative_zero_float` | `-0.0` | f64 -0.0 |
| `negative_zero_exp` | `-0e0` | f64 -0.0 |
| `negative_zero_neg_exp` | `-0.0e-0` | f64 -0.0 |
| `zero_point_zero_e_zeros` | `0.0e-` + 400 zeros | 0.0 |

**`-0` parses as a FLOAT, not an integer.** Measured: `Value` reports
`is_f64()`, value `-0.0`, for the bare token `-0`. That was worth measuring
rather than assuming -- the obvious guess is integer zero, and it is wrong,
because serde_json's negative-integer path routes a zero significand with a
minus sign to `-0.0` so that the sign survives. Any brick that touches the
integer path must not "simplify" `-0` into `0`: it would change a `Value`'s
type, its `to_string` (`-0.0` versus `0`) and its f64 bit pattern.

The exponent that *does* fail -- positive, with a non-zero significand -- is
file 19.

**Must parse.**

### 9. `s6-dup-key-last-wins.json` -- 108,891 B

One object. One key name. 10,000 members: `{"dup":0,"dup":1, ... ,"dup":9999}`.

**Last wins, and the parsed value says so.** Measured:
`from_slice::<Value>` gives `{"dup":9999}` -- a **12-byte** `Value` from a
108,891-byte document. `Map` is a `BTreeMap` by default and an `IndexMap`
under `preserve_order`; both overwrite on insert, so the outcome is the same
under either feature. Python's `json.loads` agrees.

**Prices `Map::insert` overwriting 9,999 times** -- the only file in JSONCORP
where insert is a *replace* rather than a grow, which is a different cost and
a different code path in B10's bulk-build proposal. A bulk build that sorts
and then inserts must still resolve 10,000 collisions to the same last value,
and this is the file that proves it does.

**Must parse.** Duplicate keys are legal JSON; RFC 8259 says behaviour is
unspecified, and serde_json's behaviour (last wins) is what the oracle pins.

### 10. `s6-repeated-keys.json` -- 12,491 B, depth 101

The SAME key at every level of a 100-deep nest (`{"k":{"k": ... }}`, reuse
100), and at the bottom a single object with **1,000 distinct members**
(`f0000`..`f0999`).

That 1,000-member object is the **widest object in JSONCORP**: citm_catalog's
record is 184 and twitter's `User` is 40. A per-object compare chain, a
`FIELDS` scan or a linear `unknown_field` fallback all scale with arity, and
until now the corpus stopped at 184.

**Must parse.** Depth 101 is under the limit.

### 11. `s6-structural-churn.json` -- 221,732 B

20,000 tiny empty structures in one array, drawn from a fixed pool of 20
shapes: `[]`, `{}`, `[[]]`, `[[[[]]]]`, `{"a":{"b":{"c":[]}}}`, `[{},[]]`,
`[[],{},[[]],{"a":{}}` and so on. 43,860 arrays, 25,996 objects, 33,820
commas, **zero number tokens**, and 5.43% string bytes -- all of it
single-character keys.

**94.57% structural bytes**, the highest in JSONCORP by a distance:
`s4-frame-telemetry.json` is 34.14%, canada is 9.92%. B5 (the write sink) and
B15 (punctuation handling) have never had an arm where punctuation is
essentially the entire document, and 4,016.7 key reuse over three distinct key
strings makes it a dispatch case as well.

"Many tiny documents' worth" of churn, delivered as ONE valid document so it
is a must-parse corpus member rather than a second stream. The stream case is
S5's.

**Must parse.**

## The must-FAIL files

Each carries exactly one hazard. Files 14-19 plant it in element **150 of
200** of a pretty-printed array, so the error's LINE (152) and COLUMN are both
deep in the file. An 8-byte document proves the message; only a planted one
proves the position, and "error line/col identity" is S6's actual gate.

### 12. `s6-fail-deep-array-128.json` -- 257 B

`[`x128 + `1` + `]`x128. **The first depth that fails.** 128 is
`remaining_depth`'s starting value, so `check_recursion!` reaches 0 on the
128th container.

`Err(recursion limit exceeded at line 1 column 128)`. The column was predicted
from `SliceRead::position_of_index` before it was measured, and matches:
`peek_position` is `position_of_index(index + 1)`, the offending `[` is at
index 127, so the column reads 128. It also matches upstream's own
`tests/test.rs::test_stack_overflow`.

### 13. `s6-fail-deep-object-128.json` -- 33,921 B

The same depth, as objects, pretty-printed **one level per line** so the error
lands on **line 128**, not line 1.

`Err(recursion limit exceeded at line 128 column 260)`. Predicted and
confirmed: the 128th `{` is at byte 17,145, line 128 (127 preceding
newlines), column 260 (254 bytes of indent, plus `"k": ` , plus one).

**This is the only file in the repository that tests the LINE half of
recursion-limit error identity.** Every other recursion case -- upstream's
test, `oracle::depth_documents`, file 12 -- is single-line and reports line 1,
so a line-counting regression in the recursion path was invisible until now.

Side effect worth knowing: at 97.73% whitespace it is also the
highest-whitespace file in JSONCORP (citm_catalog is 71.03%). It is a must-fail
file, so it cannot be used as a whitespace *timing* arm -- but a whitespace
brick that changes its reported column has broken something.

### 14. `s6-fail-lone-trailing-surrogate.json` -- 7,328 B

Element 150 is `"lone trailing \udc00 here"`: a trailing surrogate with no
leading one.

`Err(lone leading surrogate in hex escape at line 152 column 23)`.

**The message is upstream's and it is misleading** -- `src/read.rs` says so
itself, with an `// XXX: This is actually a trailing surrogate.` comment above
the branch. It is reproduced verbatim because the oracle's contract is
identity with upstream, not correctness of upstream's prose. If it is ever
fixed, it must be fixed in both crates in the same commit or this file fails
the gate, which is exactly the alarm you want.

### 15. `s6-fail-lone-leading-surrogate.json` -- 7,327 B

Element 150 is `"lone leading \ud800 here"`: a leading surrogate followed by a
plain byte, so the second escape never starts.

`Err(unexpected end of hex escape at line 152 column 23)`. A **different
message from file 14** for what a reader would call the same mistake, which is
why they are separate files.

### 16. `s6-fail-unpaired-hex-pair.json` -- 7,332 B

Element 150 is `"pair broken \ud800\u0041 here"`: a leading surrogate
followed by a perfectly well-formed second escape that is the wrong half.

`Err(lone leading surrogate in hex escape at line 152 column 27)`. The third
of `parse_unicode_escape`'s three failure branches, and the only one where
both escapes are syntactically valid.

### 17. `s6-fail-float-overflow.json` -- 2,603 B

Element 150 is `1e309`; the other 199 elements are the finite extremes
(`1e308`, `f64::MAX`, `4.9e-324`, `1e-400`, `-0.0`).

`Err(number out of range at line 152 column 7)` on the slice path,
**column 8 on the reader path**. `f64_from_parts` reaches an infinite `f64` and
errors rather than returning one.

### 18. `s6-fail-int-400-digit.json` -- 4,282 B

Element 150 is a 400-digit integer (about 1e399); the other 199 are the
20-digit boundary tokens.

`Err(number out of range at line 152 column 402)` on the slice path,
**column 403 on the reader path**. A different site from file 17:
`parse_long_integer` / the long-integer scratch path, not the concise one.

### 19. `s6-fail-exponent-overflow.json` -- 2,610 B

Element 150 is `1e2147483648`: an exponent that overflows i32 with a non-zero
significand and a positive sign.

`Err(number out of range at line 152 column 14)`. The third and coldest
number-range site, `parse_exponent_overflow`, reached only when the exponent's
own accumulator overflows. Its two sibling cases -- a zero significand, and a
negative exponent -- both return `Ok(0.0)` and are in file 8, so this file's
partner proves the branch is a three-way decision and not a blanket rejection.

### `RawValue` accepts every document `Value` rejects, and that is a finding

The right-hand column above is not a mistake. Measured on upstream:

| document | `Value` | `RawValue` |
|---|---|---|
| 128 nested arrays | `recursion limit exceeded @1:128` | Ok, 257 B |
| 1,000 nested arrays | `recursion limit exceeded @1:128` | Ok, 2,001 B |
| **100,000** nested arrays | `recursion limit exceeded @1:128` | **Ok, 200,001 B** |
| `"\udc00"` | `lone leading surrogate in hex escape` | Ok |
| `"\ud800x"` | `unexpected end of hex escape` | Ok |
| `1e309` | `number out of range` | Ok |
| 400-digit integer | `number out of range` | Ok |
| `1e2147483648` | `number out of range` | Ok |
| `"\uZZZZ"` | `invalid escape @1:7` | `invalid escape @1:7` |
| `"\x41"` | `invalid escape @1:3` | `invalid escape @1:3` |
| a string holding one raw 0x01 byte | `control character ... @1:2` | `control character ... @1:1` |
| `"abc` (unterminated) | `EOF while parsing a string @1:4` | same |
| `[1,]` | `trailing comma @1:4` | `expected value @1:4` |

`RawValue` capture goes through `ignore_value`, which walks the document with
an **explicit stack** (so no recursion limit applies at any depth) and does
**not** decode escapes or range-check numbers. It still rejects lexical
errors. Two of those lexical cases even disagree with `Value` on the column or
the message text -- identically on both crates, so the gate is unaffected, but
worth knowing before anyone quotes one.

Three consequences:

1. **B13's gate cannot be "`RawValue` and `Value` agree".** They provably do
   not, on eight of the nineteen files here. B13's gate is
   `RawValue` bytes identical to upstream's `RawValue` bytes.
2. **`corpus::messages()` uses the oracle's `RawValue` to slice containers.**
   That is still correct -- but it means a container whose elements would fail
   as `Value` still slices cleanly, so a per-message cell built on it must
   check the per-element parse outcome itself.
3. **A `RawValue`-based streaming consumer is a weaker validator than
   `from_slice`**, by a lot: it will happily hand a 100,000-deep document to a
   caller. That is upstream's behaviour and not this crate's to change, but it
   belongs in the README's security notes rather than being rediscovered.

### The SliceRead / IoRead column disagreement

`s6-fail-float-overflow.json` and `s6-fail-int-400-digit.json` are the only
corpus files where the two readers report **different columns for the same
error**: 7 vs 8, and 402 vs 403. `SliceRead::position()` returns
`index - start_of_line` while `IoRead` tracks its own line/column through
`LineColIterator`, and the two are off by one at the point a number is
rejected. The three surrogate files, whose error is raised at the same kind of
site, agree at column 23 and 27 -- so this is specific to the number path.

This is upstream's behaviour, identical in both crates, so `tests/oracle.rs`
passes: it compares ours-to-upstream per reader, never slice-to-reader. But it
means **a line/column quoted in the ledger must say which reader produced
it**, and these two files are where that stops being pedantry.

## Python is not the oracle

Every file is run through `json.loads`, and the generator fails if the outcome
disagrees with the file's declared Python column. Six of the eight must-fail
files parse **cleanly** under Python:

| file | Python | why it diverges |
|---|---|---|
| `s6-fail-deep-array-128.json` | **accepts** | Python's nesting limit is the interpreter recursion limit; measured on this box, `json.loads` accepts 900-deep and raises `RecursionError` at 1,000. serde_json's limit is 128 |
| `s6-fail-deep-object-128.json` | **accepts** | same |
| `s6-fail-lone-trailing-surrogate.json` | **accepts** | Python returns a `str` containing a lone surrogate. `str.encode("utf-8")` then raises, which is how the generator detects one that leaked into a must-parse file |
| `s6-fail-lone-leading-surrogate.json` | **accepts** | same |
| `s6-fail-unpaired-hex-pair.json` | **accepts** | same |
| `s6-fail-float-overflow.json` | **accepts** | Python's float saturates: `json.loads("1e309")` returns `inf`. serde_json errors rather than ever producing an infinity |
| `s6-fail-int-400-digit.json` | **accepts** | Python's ints are arbitrary precision: it returns the exact 400-digit integer. serde_json has no such fallback without `arbitrary_precision` |
| `s6-fail-exponent-overflow.json` | **accepts** | `inf`, as above |

Two more divergences affect must-PARSE files and are recorded here so nobody
uses Python to check a value:

* `s6-int-20-digit.json` -- Python parses `99999999999999999999` exactly;
  serde_json gives f64 `1e20`. Both PARSE; the values differ.
* `s6-unicode-escapes.json` / `s6-string-escape-7.json` -- Python's
  `json.dumps(..., ensure_ascii=False, separators=(',',':'))` happens to
  produce byte counts identical to serde_json's `to_string` (441,413 and
  1,029,856). That is a useful coincidence and a cross-check, not a
  guarantee; the escape SETS agree but the two writers are not the same code.

Two classes of Python divergence are deliberately **not** exercised by any
file here, and are named so the absence is a decision rather than an
oversight:

* **`NaN` / `Infinity` / `-Infinity` bare literals.** Python accepts them;
  JSON does not, and serde_json does not. They are covered as 3 of
  `oracle::EDGE_DOCUMENTS`, so a file would add nothing but a second place to
  maintain. One is cheap to add if a bulk arm is ever wanted.
* **Raw control characters inside strings.** Both parsers reject them with
  `strict=True` (Python's default, and the only mode used here), so they agree
  -- but `json.loads(..., strict=False)` accepts them, which is another reason
  the Python column is a check and not a gate.

## What S6 closes, and what it does not

**Closes.**

1. **Depth, at all.** JSONCORP's deepest document was twitter at depth 10.
   S6 spans 0 (a bare string) to 128, including the exact boundary from both
   sides.
2. **The recursion limit's error identity, including its LINE.** Upstream's
   own test and `oracle::depth_documents` are all single-line.
3. **Numbers above 8 digits.** `corpus/s4/MANIFEST.md` records that "no S4
   file can enter B4's fast path, by construction" and that S4 "bounds B4's
   regression risk; it cannot show B4 a win". S6 is where B4 can be shown a
   win or a loss: 20-digit integers, 400-digit floats, 403-byte exponents.
4. **Both number-range failure sites plus the exponent one**, and their three
   `Ok` siblings, so the branches are proven to be decisions rather than
   blanket rejections.
5. **All three lone-surrogate branches**, at a deep line and column, with
   their two different messages.
6. **Duplicate-key resolution**, pinned by a 108,891-byte document whose
   value is 12 bytes.
7. **Object arity beyond 184** (now 1,000) and **key reuse beyond 1,418.7**
   (now 10,000).
8. **The escape-density ceiling in both directions** -- 28.57% short escapes
   and 100% hex escapes -- with round-trip deltas that are arithmetic, not
   opinion.
9. **The fact that `RawValue` is not a validator.** Not previously written
   down anywhere in this repo.

**Does not close.**

1. **No invalid UTF-8 and no invalid escape SYNTAX.** Every file is valid
   UTF-8, and `"\uZZZZ"`, `"\x41"`, a raw control byte and a truncated escape
   are all `oracle::EDGE_DOCUMENTS` / `EDGE_BYTES` cases, deliberately not
   duplicated as files.
2. **No truncated document.** A stream whose last document is cut in half is a
   realistic hazard for S5's reader path and is not here. It is the most
   obvious next must-fail file.
3. **No depth between 128 and 100,000 as a `Value`**, because they all produce
   the identical error at the identical position; the `RawValue` probe above
   covers 100,000 and lives in the manifest rather than in a file.
4. **No `unbounded_depth` arm.** The feature exists (`tests/test.rs`
   exercises it at 140); a corpus file cannot express a feature flag.
5. **No `arbitrary_precision` arm.** With that feature the 400-digit numbers
   would PARSE rather than fail, which would flip files 17-19 from must-fail
   to must-parse. **The must-fail table above is stated for the default
   feature set** (`std` + `accel`; no `float_roundtrip`, no `preserve_order`,
   no `arbitrary_precision`). Any cell run under `arbitrary_precision` needs
   its own expectation table.
6. **Not timed, by design.** The gate is "cold paths stay correct and do not
   regress", so the useful S6 number is a ratio against upstream on the
   must-parse files and nothing at all on the must-fail ones.
7. **Nothing about allocation.** The 1 MB string files are the corpus's
   largest single scratch allocations and no counter reports that yet.

## Open questions -- flagged rather than guessed

Everything below was resolved by MEASUREMENT against upstream serde_json
1.0.151, but each was a genuine open question first, and the answer is
surprising enough to be worth naming:

1. **Do out-of-u64-range integers fail?** No. They parse as f64. So
   `s6-int-20-digit.json` is must-PARSE even though half its tokens are
   "outside the range". Had this been guessed the other way, the file would
   have been put in the must-fail group and the gate would have been wrong in
   the safest-looking direction.
2. **Does `1e309` become infinity or an error?** An error --
   `number out of range`. serde_json never yields an infinity from a parse.
   That single fact moved four tokens out of `s6-float-400-digit.json` into
   `s6-fail-float-overflow.json`, and it is why the float file's note says
   "expected INFINITY: none".
3. **Is `-0` an integer or a float?** A float, `-0.0`. The obvious guess is
   integer zero and it is wrong.
4. **Is depth 128 legal or not?** Not. 127 is the deepest that parses. "The
   limit is 128" reads as "128 is allowed" and it is not.
5. **Does `1e` + 400 zeros overflow the exponent?** No -- it is exactly 1.0,
   because a leading zero never advances the accumulator. And when the
   accumulator DOES overflow, the outcome depends on the significand's sign
   and the exponent's: two of the three cases are `Ok(0.0)`.
6. **Does `RawValue` enforce what `Value` enforces?** No, and not remotely --
   it accepts 100,000-deep nesting, lone surrogates and out-of-range numbers.

**Still genuinely open, and NOT resolved here:**

* **Should a 400-digit integer parse?** Under the default features it cannot
  (f64 is the only fallback) and this corpus says must-fail. Under
  `arbitrary_precision` it would parse exactly. If this crate ever ships
  `arbitrary_precision` in a default-adjacent configuration, files 17-19 need
  a second expectation column rather than an edit.
* **Is the `lone leading surrogate in hex escape` message for a *trailing*
  surrogate worth fixing?** `src/read.rs` marks it `XXX` and upstream has
  shipped it for years. Fixing it is a breaking change to error text that this
  crate's whole contract forbids doing unilaterally; it is the sort of thing
  the mission's "first upstream PRs filed" item covers, and file 14 is the
  regression test for whichever way it goes.
* **Should the `SliceRead` / `IoRead` column disagreement be reported
  upstream?** It is a one-byte difference in two number-range cases. Files 17
  and 18 pin it either way.

## Harness registration required

Nothing in `src/`, `crates/`, `docs/`, `corpus/LEDGER.md`, `corpus/README.md`,
`CHANGELOG.md` or `.github/` was touched. In cheapest-first order:

1. **`crates/rusty_json_turbo-bench/src/corpus.rs`, `all_documents()`** -- add
   `"s6"` (and `"s5"`) to the `["jsonchecker", "roundtrip"]` subdirectory
   list. That is the whole registration for the oracle: all 19 files go under
   the byte-identical gate, must-fail files included, treated exactly as
   `jsonchecker/fail*.json` already are. `all_documents()` goes from 71 to 92
   entries; assert the count so a silent skip cannot happen.
2. **Do NOT put the must-fail files in `File::EVERY`** unless
   `every_file_loads` is relaxed first: it asserts
   `bytes.len() > 1000 || f == File::S4NodeConfig`, and
   `s6-deep-array-100.json` is 201 bytes, `s6-deep-mixed-127.json` 507,
   `s6-deep-object-100.json` 901, `s6-fail-deep-array-128.json` 257. Four
   files under the bar.
3. **`oracle::number_tokens` + `check_number` is where S6's numbers earn
   most.** `number_tokens_are_bit_identical` iterates `File::ALL` (S1-S3
   only), so adding S6 to `File::EVERY` alone would NOT put its tokens under
   the number gate. Point that test at a set that includes
   `s6-int-20-digit`, `s6-float-400-digit` and `s6-exponent-zeros`, and note
   that `number_tokens` is deliberately naive: it will lift `0041` out of
   `A` in `s6-unicode-escapes.json` and hand it to `check_number`, which
   is harmless (more tokens to compare) but will add ~140,000 tokens to that
   test's `BTreeSet` and should be measured before it is merged.
4. **A must-fail LABEL the harness can see**, if S6 ever joins `File`. A
   timing verb must never try to time a document that cannot be parsed, and a
   future "everything parses" test must not treat these as defects. The
   cheapest form is `File::expects_error() -> bool`; the alternative is to
   leave the must-fail files reachable only through the directory scan in
   step 1, which is what this manifest recommends for now.
5. **`crates/rusty_json_turbo-bench/tests/s6_cold_paths.rs` already exists**
   and covers the same hazard classes with INLINE documents over three
   routes (slice, reader, and a `Dribble` reader that yields one byte per
   `read`). These files do not replace it and nothing here touches it -- the
   two are complements. The test proves the paths agree on hand-written
   cases; the corpus proves it on hashed, censused bytes at a size a test
   literal cannot carry (a 1 MB string, 174,763 hex escapes, a 128-deep
   object whose error is on line 128). The cheapest join is to point
   `agree_via` at the corpus files as an extra case list, which also puts
   S6 through the `Dribble` route that `tests/oracle.rs` has no equivalent

## Reproducing

```
python tools/gen-s5-s6.py            # write corpus/s5 + corpus/s6, print the census
python tools/gen-s5-s6.py --check    # regenerate in memory; fail if disk differs
```

The generator is deterministic by construction, not by convention: the only
entropy is `SEED_S6`, expanded by a splitmix64 written out in the file rather
than by Python's `random`; no Python float ever reaches the writer, so
`float.__repr__` cannot move a byte; dict order is insertion order; and the
two 1 MB string bodies are built from fixed tables by a per-file sub-seed.
`--check` was verified byte-identical over consecutive runs. Changing
`SEED_S6` or any of the size constants (`ESC7_PERIODS`, `UESC_TARGET`,
`N_CHURN`, `N_DUP_KEYS`, `N_BULK_*`, `WIDE_ARITY`, `DEEP`, `DEEP_MAX`,
`DEEP_OVER`, `FAIL_ELEMS`, `FAIL_AT`) invalidates every hash above, every
error column in the outcomes table, and every measurement taken against them.

**Line endings are load-bearing here in a way they are nowhere else in the
repository.** Six of these files exist to produce an exact COLUMN, and a
checkout that rewrote line endings would still make them fail -- at the wrong
position, which the oracle reports as a mismatch. `corpus/s6/.gitattributes`
marks `*.json -text`; the root `.gitattributes` already pins
`corpus/**/*.json`, and this is the local, visible statement of the same rule.

All 19 files are LF with no trailing newline.
