# S4 -- the house-payload corpus

JSONCORP's fourth scenario. Seven documents shaped like the JSON the
Remade-With-Rust house actually moves, so a brick is priced against real work
instead of against three famous outliers.

S1-S3 are `twitter.json`, `citm_catalog.json` and `canada.json`: deliberately
orthogonal, and kept that way as a gate -- a brick that helps one must visibly
not help the others. They are also not what this crate will parse in
production. No house service emits a 2.2 MB array of float pairs, and between
them the three contain **no** untagged enum, **no** `flatten` tail, **no**
`Vec<u8>` field, **no** minified body, **no** string longer than 463 bytes,
**no** `\uXXXX` escape, and nothing like the same twenty keys repeated a few
thousand times. Those are the regimes house services live in, and S4 supplies
them.

Everything here is generated by `tools/gen-s4.py` from one fixed seed
(`0x53345F484F555345`). Regenerating is byte-identical; `python
tools/gen-s4.py --check` regenerates in memory and fails if any file on disk
differs. Every number in this file comes out of that script's own census, and
the script prints the S1-S3 rows in the same tables so the comparison is not
taken on trust.

Generated, not captured. That is a real limitation and it is stated in
`Provenance` below, per shape, with the exact sentence of README or docs.rs
that grounds it.

## The files

### 1. `s4-media-probe.json` -- 531,365 B, pretty (4-space)

**Stands for** the output of `rffprobe -show_streams -show_format
-show_chapters -print_format json`, run over an ingest directory: 75 media
files, 177 streams, 88 chapters, under one scan envelope.

**Modelled on** `remade_ffmpeg_rs` (`rffprobe` grounded; field names inferred
from ffmpeg's JSON writer). The batch envelope is this corpus's construction --
a real `rffprobe` run emits one object per file, at about 5 KB. Per-message
work should be taken on a `files[i]` slice, not on the whole document.

**Shape.** Depth 6. 98 distinct keys, each used about 120 times. Max object
arity 41, which is `twitter.json`'s ~40-field `User` reproduced in a house
shape. 28.8% of its string values are numeric-shaped (`"1288530"`,
`"12.480000"`, `"0.000000"`) and a further 769 are rationals or ratios
(`"30000/1001"`, `"16:9"`, `"1/12800"`): ffprobe carries numbers as strings, so
this document has 11,806 keys and only 5,050 number tokens, none of them
floats. Windows paths (`F:\media\ingest\...`) put 606 escape bytes in.

**Prices B1 / B1s / B1v** (54.93% whitespace, 96.0% of it in runs of 5 bytes
or more, mean run 11.68, longest 25) -- a second high-whitespace file whose
non-whitespace bytes are keys and strings rather than citm's integers, which is
what lets a whitespace win be separated from a number win.

**Prices B6 / B6h** on the wide-struct axis: a 41-field object is a long
compare chain per `visit_str`, without twitter's 14.75% non-ASCII confounding
the measurement.

**Prices B4 negatively, and that is the point:** zero float tokens and all
numerics carried as strings. If a number brick moves this file, the brick is
not doing what its name says.

### 2. `s4-frame-telemetry.json` -- 596,826 B, minified

**Stands for** an encoder's per-frame statistics log: 2,600 frames of 1080p30,
one small object per frame, plus a summary.

**Modelled on** `rusty_h264` / `remade_ffmpeg_rs` (repos grounded; field names
inferred from x264's per-frame log). **The grounded twin of this shape** is
`rusty_time-api`'s `QueryReport { samples: Vec<SampleReport> }` and the
`debug.clients` MRU log (`Vec<ClientRow>`), whose field names *were* read from
docs.rs. Those are named in the mission's S4 row and are the natural addition
when `rusty_time-api` is swapped at M7; they are the same shape, so the corpus
carries it once.

**Shape.** The long homogeneous array of small objects, which is the single
most common production shape and the one S1-S3 barely have. Exactly **one**
distinct key tuple across all 2,600 frame objects, arity 18, 33 distinct key
strings in the document, average key reuse **1,418.7**. 80.3 keys/KB -- the
highest key density in JSONCORP (twitter 21.1, citm 14.9). Zero whitespace.
Mean string length 3.6 bytes.

**Prices B6 / B6d / B6h.** This is the key-dispatch file: a 33-entry
length-bucketed table hit 46,816 times. Nothing else in the corpus offers that
ratio, and B6's whole thesis is that dispatch cost scales with reuse.

**Prices B10.** 2,600 `visit_map` calls of exactly 18 entries is 46,800
`Map::insert` calls, 78.4 per KB against citm's 14.9 -- the highest insert
density in the corpus, and B10 replaces per-entry insert with a sorted bulk
build. Its `frames` array (2,600 objects) is also the `visit_seq` reserve probe
that canada's 14,310-element array of *numbers* cannot stand in for.

**Prices B14** (`deserialize_in_place` for `Vec<Struct>`): the canonical case.

**Prices B15 / B5**: 34.14% structural bytes against canada's 9.92%, and no
whitespace to hide behind, so `,` and `:` handling and `write_all` count are
visible here in a way they are nowhere else.

**Neutral arm for B1 / B1s** (0.00% whitespace) and for B4 (26,866 integers and
18,206 floats, all 3-7 digits, so the 8-digit step provably cannot fire:
`d8_hits` must read 0 while `d8_calls` is large).

### 3. `s4-signin-batch.json` -- 477,993 B, minified

**Stands for** a batch of 600 mID sign-in verifications: `SignedAssertion`
wrapping a verbatim `NonceEnvelope`, plus 12 resolved `DidDocumentV2` rosters.

**Modelled on** `mid` / `kms-types`. Field names, types and nesting are
**grounded** in docs.rs: `envelope_version: u8`, `envelope_type: String`,
`nonce: Vec<u8>`, `did`, `audience`, `purpose`, `issued_at: u64`,
`expires_at: u64`, `issuer`, `device_id`, `signature: Vec<u8>`, and
`DidDocumentV2 { did, roster_version, roster: Vec<RosterEntry>, updated_at }`
with `RosterEntry { device_id, pubkey: Vec<u8>, added_at, label }`.

**Shape, and why it matters.** serde_json serialises `Vec<u8>` as an array of
numbers. A 32-byte nonce plus a 64-byte signature is 96 integer tokens per
assertion, 33 bytes of pubkey per roster entry: **61,184 number tokens in
478 KB, 131.1 per KB, none of them floats, all of them 1-3 digits.** canada
manages 50.6 tokens/KB and they are all floats.

**Prices per-token number overhead**, which is a different axis from canada's
digit *width*: the cost measured here is `parse_integer` entry, the `peek` /
`next` / `discard` round trip and the token boundary, not the fold. B4 landed
on width; B4x was refuted because "the fold has a fixed cost that does not
shrink with width". This file is where the fixed part is 2.6x denser than
anywhere else, and it is the file that says whether that fixed cost is worth a
brick of its own.

**Prices B4 as a control:** every token is below the 8-digit path. `d8_hits`
must be 0 and stay 0.

**Prices B14** in the nested case (a `Vec` of structs each containing a struct
and two `Vec<u8>`), and **B12** over 8,592 keys of pure-ASCII base58.

**A finding, not a brick:** `Vec<u8>`-as-number-array is a house-wide wire
cost. 96 integer tokens where 88 base64 characters would do. That is a fix in
the *consumer* (`serde_bytes`, or base64 in `kms-types`), not in this crate,
and it is worth saying out loud because this crate cannot optimise its way out
of a schema decision.

### 4. `s4-sync-envelope.json` -- 212,864 B, minified

**Stands for** one HTTP response: a sidecar API envelope wrapping a SpaceDB
sync page of 280 per-entry CRDT deltas for a contact manager, plus a metering
block.

**Modelled on** `mata-oem-sidecar` (envelope: `api_version`, `served_by`,
`listen: "127.0.0.1:4243"`, `box_id`, `maker_did`, `owner_did: null`,
`pair_state: "open"`, `request_id`, `elapsed_ms`, `warnings` -- endpoint set,
identity triple and the "open" wire tag are grounded) and on `spacedb`
(collections, `CrdtType`, `Tier`, `Outcome`, capabilities with spend budgets,
k-of-n shards and placement repair are grounded; the JSON field names are
inferred, since the README shows Rust calls).

**Shape.** Depth 8 -- the deepest S4 file. 3,398 objects in 213 KB, **16.0
objects/KB**, the highest object density in JSONCORP (citm 6.3, twitter 2.0).
It is the only file in the whole corpus that contains, on purpose:

* **An untagged enum.** `fields.*` values come in four shapes -- `register`
  (`value`,`ts`,`node`), `text` (`ops[]`,`len`), `or_set` (`adds[]`,`removes[]`),
  `counter` (`delta`,`seen`) -- 1,250 of them, roughly evenly split.
* **An internally-tagged enum.** `outcome` is `{"type":"local"}` /
  `{"type":"committed","tier":...}` / `{"type":"merged",...}` /
  `{"type":"rejected","reason":...}`, 280 of them.
* **A `flatten` tail.** 565 `x_*` keys that no named field claims, spread over
  five names, so `flatten` catches them and every unmatched key takes the
  fallback path.
* **Nulls in `Option` position.** 492 of them among the entries, plus
  `owner_did: null` at the top. 1,067 literal tokens, 5.1 per KB.

**Prices B6 / B6h on the arm that can break them.** B6h's gate is "identical
`__Field` for every key including aliases; `unknown_field` text and `FIELDS`
order unchanged". A key-dispatch brick that is fast on known keys and wrong on
unknown ones passes on S1-S3 and fails here.

**Prices B10** on object density and depth rather than on array length.

**Exposes a cost class the brick catalog has no entry for.** serde's
`#[serde(untagged)]` buffers each candidate value into an intermediate
`Content` and re-deserialises it. 1,250 buffered re-parses in one 213 KB
response is not a scanning cost and no B-brick addresses it. Worth a ceiling
probe before it is worth a brick, and this is the file to probe it on.

### 5. `s4-node-config.json` -- 6,677 B, pretty (2-space)

**Stands for** a disco node's configuration file.

**Modelled on** `spacedb`'s L0-L6 layer names, `mata-oem-sidecar`'s feature
flags and catalog statuses, `deputy`'s six pipeline stages and fail-closed
gate, and `rusty_time`'s daemon and source list -- all grounded as *names*;
the config key names are inferred.

**Deliberately small, and not padded.** A config is 1-25 KB in life, which is
also the regime the mission's S4 row names for per-message latency. Padding it
to 100 KB would make it a different document measuring a different thing.

**Shape.** Depth 5, string-heavy (38.70%), 36.54% whitespace, and the corpus's
highest literal density: **11.0 literal tokens/KB** (twitter 7.5) across 72
`true`/`false`/`null`. Key reuse **1.6** against 152 distinct keys.

**Prices the cold-dispatch arm of B6.** Key reuse across S4 now spans 1.6
(here) to 1,418.7 (frame telemetry). A dispatch table that pays to build and
wins on reuse must be checked at both ends, and only this file is at the cold
end.

**Prices per-call setup cost.** At 6.7 KB, fixed cost per `from_slice` is
visible: B1s exists in its current form only because an 8-byte step on 1-byte
runs cost twitter scan 10% before the 4-byte scalar peel was added. Any brick
with entry cost -- B1s's wide scan, B10's reserve probe, a B6 table build --
must be checked here before it is believed.

**Prices B9 honestly, and only modestly.** twitter is already 3.31% literal
bytes at 7.5 tokens/KB. This file is 4.63% at 11.0/KB: 1.5x, not an order of
magnitude. S4 does not turn B9 into a measurable brick, and the ledger should
not pretend it did.

### 6. `s4-vault-shard.json` -- 439,302 B, minified

**Stands for** a k-of-n erasure shard set for an encrypted vault stripe, plus
one FFAI model shard descriptor and four hash-chained Deputy receipts.

**Modelled on** `spacedb-durability` ("k-of-n erasure shards, placement
repair", grounded), `rusty_erasure` (GF(2^8) Reed-Solomon, grounded), Deputy
(AES-256-GCM, Argon2id, SHA-256, hash-chained promotion receipts, grounded),
and FFAI's user-supplied weights (grounded). Field names inferred.

**Shape.** The opposite of twitter. 136 strings in 439 KB. Five of them are
87,384-byte base64 bodies. **99.88% of the file is string content**, mean
string length 3,226 bytes, longest **87,384** -- against twitter's longest of
463. 0.2 keys/KB. Base64 needs no escaping, so it is 349 KB of guaranteed
clean, guaranteed ASCII run.

**Prices B2.** A 16- or 32-byte string-scan step needs strings long enough to
amortise its setup. twitter's mean string is 20.4 bytes; a 32-byte step cannot
help it at all. This file is where B2's ceiling actually lives, and together
with file 7 it brackets B2's whole range: clean 87 KB runs here, an escape
every 5.7 string bytes there.

**Prices B3's clean-run maximum.** One `extend_from_slice` per 87 KB instead of
a per-byte check is the largest win B3 can ever show, so this file is B3's
upper bound and file 7 is its realistic case.

**Prices B12.** 439 KB of pure ASCII with no non-ASCII tail anywhere: the
`ascii_run_*` fast path either covers 100% of it or the census is wrong.

**Prices B7 / B13 at the seam that breaks them.** A buffered `IoRead` at
8-64 KB has a boundary inside an 87,384-byte string every single time. A
string that spans buffer refills is exactly the case a naive buffered reader
gets wrong, and `RawValue` over `IoRead` has to copy a range that outruns the
buffer.

### 7. `s4-ocr-i18n.json` -- 416,299 B, minified

**Stands for** an FFAI result bundle: 30 Carmenta OCR pages, 30 Mercury ASR
transcripts, 30 Argus captions with Diana detections.

**Modelled on** FFAI (engines, model names, the streaming/reading-order OCR
and the 32-token caption behaviour are grounded; the result field names are
inferred).

**This is a data file, not source.** The repo's ASCII-only lint governs
`src/`, `crates/` and `tools/`; a corpus file that carries real UTF-8 and real
escapes is doing its job. `tools/gen-s4.py` itself stays ASCII and writes the
non-ASCII with `\uXXXX` escapes.

**Shape -- the escape path, in both directions.** Text values are composed of
2-6 fragments drawn from three registers, so raw UTF-8 and escape sequences sit
inside one string, which is what a mixed-producer pipeline actually hands a
parser:

| Inventory | Count |
|---|---|
| `\uXXXX` escapes | 5,671 |
| of those, surrogate PAIRS (astral code points) | 1,032 |
| `\\` | 1,852 |
| `\"` | 1,604 |
| `\n` / `\t` / `\r` | 1,042 / 1,146 / 192 |
| escape bytes as a share of string bytes | **17.65%** |
| raw UTF-8 2-byte / 3-byte / 4-byte sequences | 10,452 / 8,410 / 696 |
| non-ASCII share of the file | 11.75% |
| parsed strings that need re-escaping on stringify | 1,237 of 22,809 (5.4%) |

Scripts present as raw UTF-8: Japanese, Chinese, Korean, Russian, Greek,
Arabic, Hebrew, Devanagari, Thai, Latin-1 accents, a decomposed combining
acute, U+00A0, U+2014, U+2192, U+00B1, U+2026, and three astral sequences
(U+1F680, a regional-indicator flag pair, a ZWJ sequence). The escaped register
carries the same content as `\uXXXX`, including `\u0000`, `\u000b`, `\u001b`
and correctly-paired surrogates. Every pair is checked: the generator refuses
to write an unpaired surrogate escape, because `json.load` accepts one and
serde_json does not.

**Prices B3.** 5.4% of parsed strings must be re-escaped on the way out
against twitter's 1.7%, and 17.65% escape bytes against twitter's 0.67% -- 26x
denser. B3's gate is "output identical over all 256 bytes, all escape
positions, S1/S2/S4"; this is the S4 that makes that gate mean something.

**Prices B2's dirty arm.** One escape every 5.7 string bytes stops a wide scan
constantly. Paired with file 6 this is the pair of files that decides whether
B2's step width should be 16 or 32 -- or neither.

**Prices B12** on the tail-heavy arm: 19,558 multi-byte sequences of three
different lengths, and an `InvalidUnicodeCodePoint` has to land on the same
string as upstream's does.

**Closes the corpus's largest correctness hole.** See below.

## Census

Produced by `tools/gen-s4.py`, whose `census()` is a port of
`crates/rusty_json_turbo-bench/src/content.rs`. The port is validated by the
S1-S3 rows: it reproduces the published percentages exactly (twitter
27.83 / 57.06 / 1.52 / 14.75, citm 71.86 / 12.45 / 7.14, canada 90.08). It also
asserts content.rs's own invariant on every S4 file -- whitespace + structural
+ string + number + literal bytes equals total bytes, with no byte
unaccounted.

The S1-S3 rows are the files **as the harness reads them from the working
tree**, which on this box is CRLF (see `Reproducing`).

## What S4 closes, and what it does not

**Closes.**

1. **The `\uXXXX` hole, which is the big one.** S1-S3 contain **zero**
   `\uXXXX` escapes -- twitter's 14.75% non-ASCII is all raw UTF-8, citm has
   two 2-byte escapes and canada none. So the hex-escape decoder, the
   surrogate-pair reconstruction and the scratch-buffer path they use were
   never on the timed corpus at all. Note that `docs/plans/fast_mission.md`
   section 7.2 describes S1 as stressing "Unicode escapes"; measured, it does not.
   `s4-ocr-i18n.json` puts 5,671 hex escapes and 1,032 surrogate pairs on the
   corpus.
2. **Minified input.** Four of the five biggest S4 files have 0.00%
   whitespace while still being string- and key-heavy. Before S4 the only
   zero-whitespace file was canada, which is 90% floats, so "no whitespace"
   and "all numbers" were confounded and the whitespace bricks had no clean
   neutral arm.
3. **Long strings.** Longest string goes from 463 bytes to 87,384. B2 and B3
   had no file that could amortise a wide step.
4. **The homogeneous array of small objects with identical keys**, with a key
   reuse sweep from 1.6 to 1,418.7 and key density from 0.2 to 80.3 per KB.
5. **Untagged enums, internally-tagged enums, `flatten` tails and `Option`
   nulls in wire position** -- none of which exist anywhere in S1-S3, and all
   of which the mission's own S4 row names as the point of S4.
6. **`Vec<u8>` as a number array**: 131.1 number tokens/KB with zero floats,
   isolating per-token cost from digit width.
7. **The 1-25 KB per-message regime** and therefore per-call setup cost.

**Does not close.**

1. **These are generated, not captured.** The mission's method line says "the
   house-shaped payloads (S4) are real captured messages". These are not. Field
   names are grounded where the table above says so and reconstructed
   otherwise. Real captures from `rusty_time-api`, `mid-verify` and
   `deputy-api` at M7/G8 should replace or join them, and the ledger should not
   describe the current files as captures.
2. **No `rusty_time-api` file**, though its field names are the best-grounded
   in the house. Its `QueryReport { samples: Vec<SampleReport> }` and
   `debug.clients` MRU log are the same shape as `s4-frame-telemetry`, so the
   corpus carries the shape once and names the substitution rather than
   shipping both.
3. **No 10,000-message document.** The largest arrays are 2,600 frames, 600
   assertions and 280 entries. The plan's P50/P99-over-10k cell should iterate
   the containers rather than expect 10k separate files; see registration
   below.
4. **No S5, S6 or S8.** No NDJSON stream, no `from_reader` arm, no 100-deep
   nesting, no 400-digit float, no size sweep. S4 is one document per shape at
   one size. In particular a `Vec<u8>` serialised in **pretty** mode puts one
   integer per line and is a legitimate pathological case -- it belongs in S6,
   not here.
5. **Nothing above 8-digit numbers.** No S4 file can enter B4's fast path, by
   construction. S4 bounds B4's regression risk; it cannot show B4 a win.
6. **B9 barely moves.** 11.0 literal tokens/KB against twitter's 7.5.
7. **Alias and unknown-field *error text*** is exercised only by the `flatten`
   tail; there are no serde field aliases in the data because aliases are a
   fixture-side decision, not a payload-side one.
8. **No non-UTF-8 or invalid input.** Every file is valid JSON and valid
   UTF-8. Malformed input stays S7's and the fuzzers' job.

## Harness registration required

Nothing in `src/`, `crates/`, `docs/`, `corpus/LEDGER.md`, `README.md` or
`tools/pinvs.ps1` was touched. The files are inert until the following lands.
In cheapest-first order:

1. **`crates/rusty_json_turbo-bench/src/corpus.rs`, `all_documents()`** --
   add `"s4"` to the `["jsonchecker", "roundtrip"]` subdirectory list. One
   token, and it puts all seven files under `tests/oracle.rs`'s differential
   gate immediately (bytes, `Value`, error text, float bits) with no fixture
   work. Do this first: the oracle covering S4 is worth more than any timing.
2. **`corpus.rs`, `enum File`** -- it has exactly three variants,
   `ALL: [File; 3]`, and `path()` returns `corpus_dir().join(name + ".json")`
   with no subdirectory. Needs seven variants (or a nested `File::S4(S4File)`),
   `ALL` widened, `parse()` short names (`probe`, `telemetry`, `signin`,
   `sync`, `config`, `vault`, `i18n`), and `path()` taught the `s4/` prefix.
3. **`main.rs`, `work()`** -- its `match file { Twitter | CitmCatalog |
   Canada }` for `Column::StructParse` becomes non-exhaustive the moment
   `File` grows. One arm per new file.
4. **`cells.rs`, `trait Fixture`** -- implemented for exactly three types. Until
   a fixture struct exists per file, only `dom-parse`, `dom-stringify` and
   `scan` can run on S4; `struct-parse` and `struct-stringify` cannot, and G2's
   "S4 struct parse >= 1.4x" bar is unmeasurable. Seven modules alongside
   `twitter.rs` / `citm_catalog.rs` / `canada.rs`.
5. **The fixtures must use the attributes the files exist to exercise**, or the
   payload's distinguishing shape is never entered and the `m4=0` lesson
   repeats: `#[serde(untagged)]` for `s4-sync-envelope`'s `fields.*` values,
   `#[serde(tag = "type")]` for its `outcome` and `#[serde(flatten)]
   HashMap<String, Value>` for its `x_*` tail; `Option<T>` for every null
   position; `Vec<u8>` for `nonce` / `signature` / `pubkey` in
   `s4-signin-batch` (not `&[u8]` and not `serde_bytes`, since the wire form
   under test is the number array); `String` values for `s4-media-probe`'s
   stringified numerics.
6. **The S4 latency cell** (ns per message, P50/P99 over 10k, per section 7.3) needs a
   per-message mode the harness does not have: parse `files[i]` /
   `frames[i]` / `assertions[i]` / `data.entries[i]` as a `&RawValue` slice and
   time one element at a time, cycling the 2,600 / 600 / 280 available messages
   to reach 10,000. The corpus ships containers on purpose -- 10,000 small
   files would be worse for the repo and identical for the measurement.
7. **`corpus/HASHES.txt` and `corpus/fetch.ps1`** -- S4 is generated, not
   fetched. Either extend `HASHES.txt` with the seven hashes above and teach
   `fetch.ps1` to skip `s4/`, or have it shell out to `python tools/gen-s4.py
   --check`, which is the stronger gate because it verifies the *generator*
   still produces these bytes.
8. **`corpus/README.md`** -- the scenario table has S1, S2, S3, S7 and says S4
   "lands at M1". One row.

## Reproducing

```
python tools/gen-s4.py            # write the seven files and print the census
python tools/gen-s4.py --check    # regenerate in memory; fail if disk differs
```

The generator is deterministic by construction, not by convention: the only
entropy is `SEED`, expanded by a splitmix64 written out in the file rather than
by Python's `random` (whose stream is an implementation detail); no Python
float ever reaches the writer, so `float.__repr__` cannot move a byte; dict
order is insertion order. Two consecutive runs were verified byte-identical.
Changing `SEED` or any of the seven size constants invalidates every hash above
and every measurement taken against them.

**Line endings are load-bearing.** All seven files are LF with no trailing
newline, and `corpus/s4/.gitattributes` marks `*.json -text` so no checkout can
retranslate them. This is not hypothetical: this box has `core.autocrlf=true`
and the repository has no other `.gitattributes`, which is why `twitter.json`
is 646,995 bytes in the working tree and 631,515 in `corpus/README.md`. That
delta is 15,480 carriage returns, 2.4% of the file, and the census counts every
one of them as whitespace -- so S1-S3's published byte counts and whitespace
percentages are platform-dependent today. S4's are not. (`.gitattributes` is
the one file here that is not a payload or this manifest; delete it if the
repository would rather solve this at the root, but then S4's hashes hold only
on LF checkouts.)
