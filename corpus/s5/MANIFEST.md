# S5 -- the NDJSON stream corpus

JSONCORP's fifth scenario. `docs/plans/fast_mission.md` 7.2 describes it as
"100 MB of log lines through `StreamDeserializer` over `from_reader`", pricing
`IoRead` (brick B7) and `RawValue` on Io (B13).

Every document in S1-S4 is ONE well-formed value read from a slice. S5 is the
first scenario that is MANY documents from a READER, which asks a different
question: not "how fast can we chew 600 KB" but "what does one more document
cost". Those can move in opposite directions, because per-call setup, the
buffered reader's refill boundary and the inter-document whitespace skip are
all per-document costs that a single large document amortises to nothing.

Everything here is generated by `tools/gen-s5-s6.py` from one fixed seed
(`0x53355F4E444A534E`). Regenerating is byte-identical; `python
tools/gen-s5-s6.py --check` regenerates in memory and fails if any byte on
disk differs. Every number in this file comes out of that script's own census,
and the script prints the S1-S3 and three S4 rows in the same tables so the
comparison is not taken on trust.

**Read this before reading a failure.** Both files are MULTI-DOCUMENT streams.
`from_slice::<Value>` on either one is *supposed* to fail -- a concatenation of
documents is not a document -- and the oracle compares that failure, byte for
byte, against upstream's. See `Outcomes` below for the exact messages.

## 100 MB is not checked in, and that is deliberate

The plan says 100 MB. 100 MB in git is 100 MB in every clone, every CI
checkout and every `git gc`, for a measurement whose shape is settled by
2.6 MB. So:

| | NDJSON records | NDJSON bytes | pretty docs | pretty bytes | how |
|---|---:|---:|---:|---:|---|
| checked in | 10,000 | 2,613,127 | 1,200 | 390,176 | `python tools/gen-s5-s6.py` |
| the plan's run | 410,000 | **107,338,829** | 49,200 | 15,977,171 | `python tools/gen-s5-s6.py --scale 41 --out DIR` |

Both scaled figures are measured, not projected; the run takes a few minutes
of Python and its SHA-256s are
`4b8b11463f56e3216c6930b9e646abb23cfc3ce2e1f12f185dea040e5494f395` and
`d715c617ccf7b7c9d8a29290f977864bcc178c97eb08e74790de95f8b85e6a89`.

`--scale N` emits `N * 10,000` records. It **requires** `--out DIR` and
refuses a directory inside `corpus/`, so a scaled run can never overwrite the
bytes the hashes below are taken on.

**A scaled stream EXTENDS the checked-in one; it does not replace it.** Each
record is seeded from its own index (`Rng(SEED_S5 ^ (i * GOLDEN))`), so record
*i* is the same bytes at every scale. Measured, not asserted: at `--scale 4`
and again at `--scale 41`, the first 2,613,127 bytes of
`s5-log-stream.ndjson` are byte-identical to the checked-in file, and
`--check` re-proves the property on every run (`validate_scale_prefix`). The
pretty stream is identical up to the end of document 1,199; only its 6
trailing whitespace bytes become a separator once more documents follow.

At scale 41 the line band widens to 151..400 bytes (mean 260.8) -- still
inside the [150, 400] bound the generator asserts on every record.

So a 100 MB number and a 2.6 MB number are taken on the same documents, and
the small file is a true prefix of the large one. That is what makes the
checked-in file a legitimate stand-in rather than a different corpus.

## The files

### 1. `s5-log-stream.ndjson` -- 2,613,127 B, 10,000 documents

**Stands for** a house log or telemetry sink: newline-delimited JSON, one
complete object per line, no enclosing array, as `tracing`'s JSON layer and
every log shipper in the world emit it.

**Line length is the point.** 159 to 400 bytes, mean 260.3. That band is where
log lines actually live, and it is held by construction: the generator adds or
drops ONE field after building a record and asserts the result is inside
[150, 400], so no template needs hand-tuning and no line can drift out of the
band when the seed changes.

**Shape.** Depth 2 -- a record, and one nested field bag (plus an `err` object
on warn and error). 21,421 objects, no arrays at all. Whitespace is 10,000
bytes: the newlines, and *nothing else*. Every other byte is payload.

| Inventory over 10,000 lines | |
|---|---:|
| distinct targets | 14 |
| `info` / `debug` / `warn` / `error` / `trace` | 6,049 / 1,985 / 1,137 / 284 / 545 |
| lines with a `trace` id (a 26-char ULID) | 8,473 |
| lines whose `err` is an object | 1,421 |
| lines whose `err` is `null` | 8,579 |
| lines carrying a `\` escape (Windows paths) | 1,370 |
| lines carrying raw non-ASCII (accented device labels) | 225 |
| distinct key strings | 76 |
| key reuse | **1,599.0** |

**Prices B7 (buffered `IoRead`) at its real workload.** The whole file is
10,000 documents of ~261 bytes. An 8-64 KB buffer therefore holds 30 to 250
complete documents and the refill boundary lands *between* documents about 40
to 320 times, and *inside* one the rest of the time. `s4-vault-shard.json`
puts a boundary inside an 87 KB string, which is the hard case; this puts one
at a document seam 10,000 times, which is the common case. Both are needed:
one is about a string that outruns the buffer, the other is about the
per-document bookkeeping the reader has to get right every 261 bytes.

**Prices B13 (`RawValue` over a reader) with the count that matters.**
Measured against upstream: `Deserializer::from_reader(...).into_iter::<Box<RawValue>>()`
yields **10,000 raw documents holding 2,603,127 bytes** -- the file minus
exactly its 10,000 newlines. A `RawValue` streaming consumer is the shape a log
pipeline actually has (route on `tgt`, keep the body verbatim), and this is the
only file in JSONCORP that has 10,000 of them.

**Prices per-document overhead, which nothing else in JSONCORP can.** 10,000
documents at 261 bytes each in one 2.6 MB file. `s4-node-config.json` (6.7 KB)
prices per-`from_slice` setup at *one* call; this prices it at 10,000 calls
through a reader, with the setup that a reader has and a slice does not.

**Also the corpus's key-reuse record.** 121,521 keys over 76 distinct strings
is a reuse of 1,599.0, above `s4-frame-telemetry.json`'s 1,418.7. If a key
dispatch brick is ever revived after M4's refutation, this is the file with the
most to give it -- and, at 47.6 keys/KB against telemetry's 80.3, it says
whether the win tracks reuse or density.

**Anti-amortisation arm for B2.** Mean string 9.2 bytes, longest 53. A 16- or
32-byte string-scan step cannot pay for its setup anywhere in this file, which
is exactly why it belongs next to `s4-vault-shard.json`'s 87 KB runs.

**Ends WITH a newline**, unlike all seven S4 files. Deliberate: a log file
does, and trailing whitespace after the last document is its own
`StreamDeserializer` path -- the iterator must return `None`, not an error.
Measured: it returns `None`.

### 2. `s5-log-stream-pretty.json` -- 390,176 B, 1,200 documents

**Stands for** the same data from a producer that pretty-prints, concatenated
into one stream. Whitespace between documents, and inside them.

**Same data, checked.** These are the first 1,200 records of the NDJSON file,
pretty-printed at 2-space indent. The generator parses both files and asserts
the document sequences are equal (`validate_pair`), so "same data" is a
verified property, not a claim. It is a PREFIX of the NDJSON file's records,
not all 10,000 of them: pretty-printing all 10,000 would add 3.3 MB to the
repository to re-measure a whitespace path that 1,199 separators already
cover.

**The inter-document whitespace is the file's whole reason to exist.**

| | |
|---|---:|
| documents | 1,200 |
| leading whitespace, before the first document | 5 bytes (space, space, LF, tab, LF) |
| trailing whitespace, after the last | 6 bytes (LF, LF, space, space, tab, LF) |
| separators | 1,199 |
| separators that are EMPTY (`}{`, documents butted together) | **115** |
| separator bytes total / longest | 2,754 / 5 |
| `\r` bytes in the file | 241 |

Ten separator shapes are drawn from a fixed pool: `""`, `"\n"`, `"\n\n"`,
`" "`, `"\t"`, `"\r\n"`, `"\n  \n"`, `" \t \n"`, `"\n\r\n\t "`, `"\n\n\n"`.

**`""` is in that pool on purpose.** `}{` with no separator at all is a
distinct path and the one a naive stream reader gets wrong; `{}{}` exists in
`oracle::EDGE_DOCUMENTS` as an 4-byte case, and this file has 115 of them
between real documents.

**`\r` is in that pool on purpose too**, and its count is published above so it
can be checked. It is JSON whitespace, `corpus/s5/.gitattributes` pins it, and
it is the only carriage return anywhere in the benchmark corpus now that the
root `.gitattributes` has stopped S1-S3 acquiring 15,480 of them by accident.

**Prices the whitespace skip in front of a document**, which is not the same
code as the whitespace skip inside one. `s4-media-probe.json` is 54.93%
whitespace in runs averaging 11.68 bytes -- all of it *inside* one document.
This file's separator runs are outside every document, and 115 of them are
zero bytes long, which is the case a "skip at least one" implementation gets
wrong.

**Prices `RawValue` with whitespace to exclude.** Measured: 1,200 raw
documents holding 387,411 bytes of a 390,176-byte file. The 2,765 bytes left
behind are exactly the leading, trailing and separator whitespace. A `RawValue`
that captured a byte of it would show up here immediately.

## Outcomes, measured against upstream serde_json 1.0.151

Not predicted. Produced by a throwaway binary in the scratchpad that links
upstream `serde_json` 1.0.151 with `raw_value` and reports every path the
oracle compares.

| file | `from_slice::<Value>` | `from_str` | `from_reader` | `StreamDeserializer` (slice) | (reader) | `RawValue` (reader) |
|---|---|---|---|---|---|---|
| `s5-log-stream.ndjson` | `Err(trailing characters at line 2 column 1)` | same | same | **10,000 items, then `None`** | 10,000, `None` | 10,000 docs, 2,603,127 B |
| `s5-log-stream-pretty.json` | `Err(trailing characters at line 19 column 3)` | same | same | **1,200 items, then `None`** | 1,200, `None` | 1,200 docs, 387,411 B |

**Both files are must-parse under `StreamDeserializer` and must-FAIL under
`from_slice`.** That is not a defect and not a contradiction: it is what a
document stream is. Every S5 error above is a `Category::Syntax` "trailing
characters", identical on both crates and on all three readers, which makes it
a *valuable* corpus member -- `trailing characters` is the error a real
consumer hits the moment it calls the wrong function, and its line and column
are now pinned by the gate.

Python agrees exactly: `json.loads` on either whole file raises `Extra data`,
and `json.JSONDecoder().raw_decode` in a loop finds 10,000 and 1,200 documents
respectively. The generator asserts both.

## What S5 closes, and what it does not

**Closes.**

1. **The reader path, at all.** Before S5 the only `from_reader` coverage was
   `oracle::check_document` running it over single-document files. There was
   no scenario whose shape *requires* a reader.
2. **Multi-document input.** `oracle::EDGE_DOCUMENTS` has `"{}{}"` and
   `"1 2"`. This is 10,000 and 1,200 documents, with ten separator shapes,
   leading and trailing whitespace, and 115 empty separators.
3. **Per-document overhead** at 10,000 documents, and the 150-400 byte
   regime, which is smaller than any S4 file and is where a log line lives.
4. **`RawValue` at volume over a reader**, with a measured byte count that a
   regression would break immediately.
5. **1-byte whitespace runs as the only whitespace**, which no other corpus
   file offers.
6. **The plan's 10k-message count**, on real separate documents rather than
   by iterating a container. `corpus/s4/MANIFEST.md` had to say "the plan's
   P50/P99-over-10k cell should iterate the containers"; it no longer does.

**Does not close.**

1. **Generated, not captured.** The line shape is `tracing`'s JSON layer
   rearranged; no house log format was read. See `Provenance`.
2. **Depth 2.** A log line is flat by nature, so S5 adds nothing to the depth
   axis -- that is S6's job.
3. **No non-UTF-8, no invalid document, no truncated final line.** Every
   document parses. A stream whose last line is cut in half is a realistic
   hazard and is NOT here; it belongs with S6's must-fail group or the
   fuzzers, and it is listed in `corpus/s6/MANIFEST.md`'s open questions.
4. **No slow or chunked reader.** Both files are read from a `Cursor`,
   which refills in one shot. A reader that hands over one byte per `read`
   is a different test of B7 and needs harness code, not a corpus file --
   and it already exists: `Dribble` in
   `crates/rusty_json_turbo-bench/tests/s6_cold_paths.rs`. Pointing it at
   these two files is the S5 arm that a `Cursor` cannot express.
5. **No 100 MB bytes in git.** By design; `--scale 41` reproduces them.
6. **Nothing above 8-digit numbers**, so B4's fast path cannot fire here
   either. S5 bounds B4's regression risk; it cannot show B4 a win.

## Harness registration required

Nothing in `src/`, `crates/`, `docs/`, `corpus/LEDGER.md`, `corpus/README.md`,
`CHANGELOG.md` or `.github/` was touched. The files are inert until the
following lands. In cheapest-first order.

1. **`crates/rusty_json_turbo-bench/src/corpus.rs`, `all_documents()`** -- add
   `"s5"` (and `"s6"`) to the `["jsonchecker", "roundtrip"]` subdirectory
   list. That puts every file under `tests/oracle.rs`'s differential gate with
   no enum or fixture work, exactly as S4's registration note recommends, and
   it treats a must-fail file the way `jsonchecker/fail*.json` is already
   treated: error text compared, not success assumed.
2. **`json_files_in()` filters `p.extension() == "json"`, so
   `s5-log-stream.ndjson` would be SILENTLY SKIPPED.** This is the one blocking
   change: widen the filter to `"json" | "ndjson"`. A skipped corpus file is
   the `m4=0` lesson in its purest form -- the gate passes and covers nothing.
   Assert the count: adding `s5` and `s6` to the list must take
   `all_documents()` from 71 to 92 entries.
3. **`tests/oracle.rs` cost.** `check_document` builds a `String` describing
   every stream item. For `s5-log-stream.ndjson` that is a ~2.6 MB string on
   each side, plus 10,000 `Value` allocations, twice. It passes, but it is the
   most expensive single document in the corpus by an order of magnitude, so
   expect the oracle test's wall time to move and record it.
4. **`enum File` + `Scenario`** -- only needed for TIMING. Two variants
   (`S5LogStream`, `S5LogStreamPretty`), a `Scenario::S5`, `parse()` short
   names (`ndjson`/`stream`, `pretty-stream`), and -- note -- `path()` builds
   `format!("{}.json", name())`, which cannot express `.ndjson`. It needs a
   `file_name()` or an `extension()` per file.
5. **`corpus.rs` tests break.** `every_file_loads` asserts
   `bytes.len() > 1000 || f == File::S4NodeConfig`; `scenarios_partition_every`
   asserts `S1_S3 + S4 == EVERY`. Both need widening the moment `File` grows.
   (S6 makes the first one bite hardest: `s6-deep-array-100.json` is 201
   bytes.)
6. **`main.rs`, `work()`** -- its `match file { ... }` for
   `Column::StructParse` becomes non-exhaustive as soon as `File` grows.
7. **A stream verb, which does not exist.** `corpus::messages()` slices a
   container by JSON path (`File::message_array`). S5 has no container: the
   documents ARE the file. The S5 cell needs a sibling --
   `corpus::stream_documents(file) -> impl Iterator<Item = &[u8]>` -- and the
   cell itself must be able to run three arms over the same bytes:
   `from_slice` per document, `StreamDeserializer::from_slice`, and
   `StreamDeserializer::from_reader` with a stated buffer size. The plan's
   ceiling measurement for B7 is exactly the ratio between the last two.
8. **A `LogRecord` fixture** in `cells.rs` for `struct-parse` /
   `struct-stringify`: `ts`/`lvl`/`tgt`/`msg` as `String`, `trace` as
   `Option<String>` (15% of lines omit it), `span` as `String`, `fields` as
   the thing under test -- either a typed per-target enum or
   `HashMap<String, Value>`; `err` as `Option<ErrObj>` with
   `retry_in_ms: Option<u64>`. The `Option` positions are load-bearing: 1,527
   lines omit `trace` and 8,579 have `err: null`.
9. **`corpus/HASHES.txt` and `corpus/fetch.ps1`** -- S5 is generated, not
   fetched. Either add the two hashes above and teach `fetch.ps1` to skip
   `s5/`, or have it shell out to `python tools/gen-s5-s6.py --check`, which is
   the stronger gate because it verifies the *generator* still produces these
   bytes.
10. **CI** -- add `python tools/gen-s5-s6.py --check` next to the existing
    `gen-s4.py --check` step.
11. **`corpus/README.md`** -- one row. Note the `.ndjson` extension in it, so
    nobody writes another `*.json`-only glob.

## Reproducing

```
python tools/gen-s5-s6.py                        # write corpus/s5 + corpus/s6
python tools/gen-s5-s6.py --check                # regenerate in memory; fail on any diff
python tools/gen-s5-s6.py --scale 41 --out DIR   # ~102 MB, the plan's S5 run
```

The generator is deterministic by construction, not by convention: the only
entropy is `SEED_S5`, expanded by a splitmix64 written out in the file rather
than by Python's `random` (whose stream is an implementation detail); no
Python float ever reaches the writer, so `float.__repr__` cannot move a byte;
dict order is insertion order; and every record's seed is a pure function of
its index. `--check` was verified byte-identical over two consecutive runs.
Changing `SEED_S5`, `N_LOG_LINES`, `N_PRETTY_DOCS`, `LINE_MIN`/`LINE_MAX`, a
target template or the separator pool invalidates both hashes above and every
measurement taken against them.

**Line endings are load-bearing, and `.ndjson` is the new hazard.**
`corpus/s5/.gitattributes` marks `*.json -text` AND `*.ndjson -text`. The root
`.gitattributes` already pins `corpus/**/*.json`, but not `*.ndjson` -- and
this file is 10,000 line endings, so a `core.autocrlf=true` checkout would add
10,000 carriage returns, grow it by 10,000 bytes, triple its whitespace share,
change both `StreamDeserializer` byte offsets and the hash, and quietly
benchmark a different document. That is not hypothetical: it is precisely what
happened to `twitter.json`.
